# S6 歌曲数据库补全与更新执行指南

版本：v1.3 · 2026-09-03（适配约4,000首及后续增量，含四项表演参数评估）  
目标仓库：`idol-producer-web`  
建议将本指南放入：`support/reports/scenario6-song-update-guide.md`  
已知输入：`support/reports/scenario6-song-enrichment-input.json`  
S6 开档日期：**2025-07-05（日本当地日期）**

## 1. 任务与执行范围

请在本地 repo 实际执行：检查输入和现有数据 → 统计缺口 → 检索证据 → 补全歌曲 → 评估歌唱／舞蹈难度及 lead 数量 → 合并可确认事实与明确标识的游戏估计 → 验证 → 输出结果与剩余问题。不要只给出另一份计划。

用户确认：输入 JSON 包含已有歌曲资料，以及 S6 活跃团和未来出道团；已经进入可玩名单的团歌曲相对齐全。因此本次主要补普通 AI 团及其他资料不足团，同时检查可玩团已有数据的时间边界和明显错误。

本指南编写时未读取该 JSON 本体及当前 repo schema。以下字段、状态名和输出路径是工作规范建议，**不能当成现有实现**。先适配仓库，不要为套用示例重构数据库。

默认完成本地数据更新、必要的小型兼容修改、审计与验证；不包含部署、推送、发布、购买 API 服务或大规模游戏机制开发。保留用户工作区里的其他改动。遵守实际 repo 的 `AGENTS.md` 与更近的用户指令。

目标是形成足以支持 S6 的有证据歌曲库，并明确哪些歌能在开档使用、哪些属于未来、哪些仍待确认。无需追求所有团的完整百科，也不能把未查到误记为没有。

用户补充：当前已有近 **4,000 首**，未来还会增加。因此第10节的完整听看规则用于有证据评估，不作为全库扫描的前置条件；批量执行以第15节为准。不能要求人工完整看完每一首，才让数据库进入可用状态。

## 2. 先检查实际仓库

1. 阅读适用的 `AGENTS.md`，检查 git 状态；用 `rg` 定位输入文件、生成脚本、歌曲与团体 canonical 数据、schema/type、S6 loader、歌曲可用性筛选和现有验证命令。
2. 读取输入 JSON 的元数据、顶层结构和实际记录。检查生成时间、场景日期、团体与歌曲 ID、歌曲是内嵌对象还是引用、是否存在快照/导出过滤。
3. 查明权威数据流：人工维护源 → 生成器 → 导出/运行时数据。输入报告不自动等于写入目标；若是生成物，应更新上游并用原脚本重建。
4. 核对输入与当前 canonical 数据的版本差异。以稳定 ID 关联，报告输入遗漏或过期记录，避免用旧快照覆盖新数据。
5. 确认可玩、可选择、普通 AI、未来出道等分类的真实来源。不要根据歌曲数、团名或当前现实名气推断游戏分类。
6. 核对 S6 的团体存续、出道、重启及版本语义。成立/发表不等于舞台出道；官方宣传帐号存在也不等于开档已有可演出曲库。

没有找到 canonical 写入目标时，仍完成研究与可审阅的候选补丁，并说明定位障碍；不得随意新建第二套正式歌曲数据库。

## 3. 基线审计与缺口报告

在修改前保存输入身份（路径、内容哈希、可取得的生成时间、git revision）及统计。未提交数据用文件哈希补充，不把 HEAD 当成工作区内容版本。

每团至少统计：

| 内容 | 解释 |
| --- | --- |
| group ID / 正式名称 / 别名 | 复用现有身份；搜索别名不生成重复团 |
| S6 状态 | 开档活跃、未来出道、边界待核、其他；与 repo 状态映射 |
| playable / selectable / tier | 读取实际配置，注明 tier 对应日期 |
| 原始关联数 / 去重歌曲数 | 分开曲目关联、歌曲实体和发行版本 |
| S6 可用曲数 | 有证据在开档前或当日已可由该团演出 |
| 未来歌曲数 / 日期不明数 | 不与开档曲数混算 |
| 歌名、日期、团体归属、来源缺失数 | 按字段分别统计 |
| 本轮样本覆盖 | setlist 数、时期、来源和抽样偏差 |
| 待处理状态 / 下一步 | 缺歌、缺日期、去重冲突、来源不可访问等 |

汇总列出总团数、活跃/未来团数，以及各类团中开档确认曲数为 0、1–5、6–10、11+ 的分布。**分桶只是诊断指标，不是完整度等级**：新团有三首可能已全，老团有三十首也可能缺大量曲目。

没有可信总曲数时，不给“已完成 80%”之类比例。可分别报告“有至少一首确认曲的团体占比”“已完成本轮检索的团体占比”，注明分母；它们不是曲库完整率。

现有数据很多只能称 `existing_catalog_substantial` 等描述性状态；只有具备截至指定日期的较完整官方曲目清单并完成对照，才标记相应范围内已核全。几场 setlist 不能证明完整。

## 4. 分层与处理顺序

以下是本次研究深度建议，不是新增游戏系统：

| 层次 | 对象 | 本轮核心内容 |
| --- | --- | --- |
| Lite | 所有输入团体 | 歌名、团体关联、来源、日期证据、原创/翻唱关系（可未知）、开档/未来可用性 |
| Standard | repo 已定义的 C 档及以上、重要竞争团、关键场景团 | Lite + 可确认的发行/制作信息、MV、历史 setlist 样本和常用曲观察 |
| Full | 可玩/可选择团 | 上述事实 + 三项难度与 lead 数量优先复核；已有人工参数保持，逐人 part/完整站位另列专项 |

若 tier 使用 C−/C/C+，按 repo 的排序和层级语义归类；不能做字符串比较，也不能拿 2026 tier 替代 2025 tier。

优先顺序：

1. 开档活跃但确认曲为 0 的重要竞争团及可玩/可选择团。
2. 开档活跃、确认曲仅 1–5 首且有明显缺口的团。
3. 其他活跃团的缺曲和关键日期问题。
4. 未来出道团的身份、出道信息与未来曲目隔离；不要为其填造开档曲库。
5. 相对完整团的低成本去重、别名、日期和来源修正。

先让所有输入团获得一次身份与基础来源检查，再按上述顺序深入。每团设置可复现的搜索预算；例如首轮查官方目录/发行目录及两组历史搜索，深入轮尝试取得 10–30 场历史 setlist。此数值是检索预算，**不是最低入库门槛或完整性证明**。资料不足就记录不足，继续下一团。先按第15节做小规模试跑，实际耗时或访问条件不支持时缩减检索深度，并保留范围说明。

## 5. 搜索与证据采集

### 5.1 先利用 repo 已有资料

检查现有歌曲文件、报告中的直接来源、官方链接和已整理 setlist。只复用与当前命题、版本和日期相符的材料。若有 `idol-data-lab` 本地或授权远程数据，可用于身份及既有曲名交叉核对，但不要无理由改动另一个 repo。

旧更正日志不作为常规内容检索源；查询当前有效结论及其证据。更正关系只用于审计。

### 5.2 外部来源按所证明的字段选择

| 来源 | 适合确认 | 不能直接推出 |
| --- | --- | --- |
| 官方网站、运营/成员公告 | 新曲、初披露、作品归属、实际或计划日期 | 计划已实际执行 |
| 官方 X setlist、官方现场录像 | 该团在某场实际演出某曲 | 原创归属、正式发行日、首次披露日 |
| 官方 discography、厂牌、发行商/TuneCore 页面 | 发行版本、曲名、发行日期、明确列出的 credits | 首次现场日期、当时常用频率 |
| 官方 YouTube MV/音源 | 曲名、作品信息、视频版本 | 上传日就是发行日/初披露日 |
| Apple Music、Spotify、OTOTOY、mora 等目录 | 候选曲、发行元数据及交叉核对 | 当前目录等于 2025 曲库、合集日期等于原曲日期 |
| 媒体报道、活动资料 | 对特定作品/演出的明确记载 | 未写出的主唱、center 或原唱归属 |
| 粉丝 setlist、评论时间轴 | 候选曲及现场观察线索 | 自动获得官方核验等级 |

并非所有平台都必须查询；能用少量可靠来源确认就停止重复查证。搜索结果摘要用于定位，尽量打开实际页面再确认。打不开正文时如实保留为线索，不冒称已读原始来源。

建议查询组合：正式团名/曾用名 + `セトリ`、`セットリスト`、`新曲`、`初披露`、`配信`、`discography`，以及官方帐号和已发现歌名。使用日期筛选，但以原帖/活动的实际日期为准。不要把文件中未核实的社交帐号当成官方。

历史常用曲首选 **2025-01-01 至 2025-07-05**，不足时扩到 **2024-07-05 至 2025-07-05**，并按该团成立/出道日期截取。更早资料可证明旧歌存在。2025-07-05 后资料可用于回溯证明早期事实，但不能用后来新曲或后来频率覆盖开档世界。

若 X 不可访问，不要把任务卡在抓取上。使用可访问的官方目录、发行资料、视频和可靠报道补基础曲库，明确“未取得足够历史 setlist”。没有样本就不生成历史频率。遵守平台访问规则，不购买服务或绕过登录/访问控制。

## 6. 时间语义：最高优先级的数据约束

必须区分下列概念，具体字段名沿用 repo；缺少容纳位置时记录在研究 sidecar 中：

| 日期概念 | 含义 |
| --- | --- |
| first_performed / first_unveiled | 有明确证据的首次演出/初披露，二者也可能不同 |
| release_date | 某个发行版本的正式发行日 |
| first_observed / last_observed | 本次样本中最早/最晚观察日期，不是真实首末演出日期 |
| announcement_date / planned_date | 发表日与计划日，不代表实际发生 |
| available_from | 游戏使用的可用起点及推导依据，不能伪装成史实首演日 |

规则：

- 2025-06 已有该团现场证据、2025-08 才配信的歌曲，可以是 S6 开档已有歌。若真实初披露日未知，只记录“至迟于观察日已存在”，不能将 6 月观察日写成首次披露。
- 2025-08 才初披露的歌不能进入 7 月 5 日开档曲库。若只是 8 月发行、初披露未知，则不能仅凭发行日期断言此前不存在，应列为时间待核。
- 日期未知的歌不得默认早于开档；不填 `1970-01-01`、开档日或伪造的月初日期。若只有年份/月，保留日期精度或范围；跨越开档日的区间保持待核。
- 开档当日资料遵循 repo 的日内/按日规则；若只按日模拟，可包含当日已确认发生的事件并说明约定。计划公告本身不构成已发生证据。
- 未来团与未来歌单独保留，沿用 repo 已有历史事件/解锁机制。若机制不存在，本次先保存在研究候选中，不创建强制历史发行系统，也不暴露到开档 loader。
- 后来团体继承旧团作品、重启、改名、共享曲库，都要分别核对作品身份与该团可用日期；原曲早已发行不等于接手团开档能唱。
- 较晚发布的官方回顾可以证明较早演出，但分别记录页面发布时间与所述事件日期。

## 7. 歌曲身份、版本与去重

1. 优先复用稳定 song ID 和 group ID；不要以列表顺序生成会漂移的 ID。
2. 标题建立原文、正式显示名和搜索别名。全半角、空白、大小写等规范化只用于候选匹配；符号、假名差异可能有语义，不能直接改显示名。
3. 同名不同曲、同一团翻唱同名歌均需来源确认。模糊匹配只输出候选，不自动合并。
4. 单曲/专辑重复收录通常是同一作品的发行关系；instrumental、off vocal、live recording、remix、重录版是否单独实体，沿用 repo 既有约定。
5. 团体演出记录不证明原创。`original / cover / shared / unknown` 等只是概念示意；只有证据够时才确认 original。版权权利与游戏可唱关系分开，不由 setlist 推断授权。
6. SE、MC、视频、未命名串烧片段、成员 solo、生日限定翻唱分别识别。不要把它们全部当常规团体原创；具体收录范围沿用现有规则。
7. 历史旧曲在近期样本没出现，不能据此删除、标废弃或禁止 AI 使用。可以记录“近期样本未观察到”。

## 8. 证据与不确定性记录

每项新增/更正的关键事实应能追溯到：**命题、歌曲/团体、适用日期或版本、证据类型、核验状态、来源、采集日期**。

为避免污染游戏 schema，优先复用 repo 的来源存储方式；如无则建立研究 sidecar，保存字段级证据，而非为每首歌硬塞一个全局 confidence。

建议的概念结构（不是强制 runtime schema）：

```json
{
  "groupId": "<existing-group-id>",
  "songId": "<existing-or-stable-new-song-id>",
  "claim": "该团至迟于该日期已演出此曲",
  "field": "observed_performance",
  "value": "<verified-event-date>",
  "sourceUrl": "<actual-opened-source-url>",
  "sourceType": "official_setlist",
  "verificationStatus": "primary_source_checked",
  "retrievedAt": "<actual-retrieval-date>",
  "notes": "该日期不是首次披露日"
}
```

来源类型和核验状态分开。粉丝记录即使已读也仍是社区观察；多平台复制相同发行资料不算多个独立来源。记录理由比“置信度 0.9”更有用。

冲突保留双方来源和待决字段，不能静默选一个。人工校准值及有证据旧值不被批量重写；强证据支持更正时保存 old/new/reason/source。未知字段在研究层用 null/省略表达；runtime 若不支持 null，不要盲目写入，使用既有兼容方式或暂存候选。

不要复制整段歌词或整篇媒体文章进新报告。事实补全通常只需元数据、简短证据摘记和直接链接。需要作品评价时先读歌词与相关制作/现场资料，按项目现行框架处理。

## 9. setlist 样本与频率（有样本才执行）

每场记录团体、实际日期、活动/场馆、场次、来源、完整/部分状态、曲目顺序、encore/solo/cover/medley。无法取得的项留空，不编造。视频时间戳是视频相对位置，不是现实演出时刻。

按团体 × 日期 × 活动 × 场次去重；官方帖、粉丝帖、视频可能描述同一场。无法确定是否重复时先隔离，避免重复计数。串烧中可识别的片段单独标记；默认不混入完整歌曲计数。

分别保存：

- `sampled_show_count`：纳入该统计的独立完整 setlist 场次。
- `song_show_count`：其中包含该曲的场次；同场多次演出在此只计一次。
- `performance_count`：曲目的实际演出次数；确实返场重唱可大于场次数。
- `show_presence_rate = song_show_count / sampled_show_count`：样本场次出现率，各曲之和可超过 100%。
- `slot_share = performance_count / 全部纳入曲目的演出次数`：样本曲目席位占比；写清是否排除 solo、cover、SE 等。

部分 setlist 可以证明“出现过”，但缺失项不能当作没演过；默认不与完整 setlist 共用频率分母。记录窗口、样本来源、one-man/对邦/生日场等构成；来源偏向某类场次时明确提示抽样偏差。

这些数值是**样本统计**，不是实际全期演出频率，也不是歌曲人气。禁止用 MV 播放量替代现场频率。

AI 选曲权重只有在 repo 已支持时，才按现有定义导入合格样本或经明确规则转换；保留样本与模型参数的区别。没有样本时保留现有游戏 fallback，并标为模拟默认值。本次不为接入 `live_repertoire_weight` 重写选曲系统。

## 10. 歌唱／舞蹈难度与 lead 数量：本轮评估方法

### 10.1 先明确五个输出代表什么

用户要求本轮尝试确定以下四项，不能全部推迟到后续。其性质是**基于可观察作品要求的游戏参数**，通常不是可以从发行目录直接抄取的官方事实。

| 输出 | 评估对象 | 不等于 |
| --- | --- | --- |
| singing difficulty | 指定版本唱出旋律、节奏、气息与关键段落的要求 | 这次现场唱得好坏、歌曲质量 |
| dancing difficulty | 单人成套动作的控制、协调、节奏和持续执行要求 | 视觉热闹程度、全员队形移动 |
| sing-lead count（1–3） | 本版本需要设置的关键歌唱职责席位数 | 有独唱 part 的人数、官方主唱头衔 |
| dance-lead count（0–3） | 本版本需要设置的关键舞蹈职责席位数 | 前排人数、跳舞最好的成员数 |

沿用 repo 的真实字段、数值范围和含义。先读 performance 计算代码，确认现有歌舞难度是否已经分别作用于 lead 与全员，是否已有阵型熟练度。不能仅因字段同名就把本指南不同含义的数值写进去。

如果当前字段无法表达区别，先输出带语义说明的 assessment sidecar；只有明确映射后才导入，必要时做最小适配。歌曲仍可保存 formation 供展示、曝光位置和队形熟练度使用，但 formation **没有独立难度数值**，也不作为歌曲能力门槛。**本指南不修改现行作品六项评价或 Live 综合体验公式，也不创造新的综合体验权重。**

### 10.2 把作品要求与成员表现分开

评估标准为：合适阵容、已熟悉作品、无明显伤病疲劳情况下，按选定版本完成表演需要什么。不要因为一位强主唱唱得轻松就降低歌曲难度，也不要因为新人演砸而抬高难度。

内部评估同时记录两个层面，即使 runtime 目前只有一个难度字段：

- **全员/一般 part 基础负荷**：多数成员在普通段落需要完成的要求。
- **关键段落峰值要求**：少数 lead 或全员在落サビ、高音长句、dance break 等段落的要求。

同一首歌可以“普通 part 较易、sing-lead 峰值高”；不能把一处高音变成全体成员都必须满足的高门槛。如果 runtime 仅有一个用于全员的难度，就不要直接用 lead 峰值覆盖，保留峰值到 sidecar 并报告表示限制。

歌唱难度先评声乐任务本身；再单列“关键唱段与大动作/移动是否重合”的唱跳负荷观察。舞蹈耐力、当天疲劳和这一重合负荷不可在多个字段重复加罚。主唱在高难段减舞，应按实际指定编舞评估，不假定全员动作都一样。

作品难度不等于学习天数；熟练度、学习率与长期能力沿用现有系统。formation 和队形熟练度继续沿用现有系统，本轮不把队形复杂程度换算为难度值。

### 10.3 来源与可观察范围

优先顺序按任务不同选择：官方完整音源/歌词/可用乐谱用于唱；Dance Practice、Dance Shot、固定全景完整舞台用于舞蹈与阵型；多机位 live 用于补充；MV 与短视频只支持实际展示的段落。

先明确歌曲、音源版本、编舞版本、阵容人数及适用时期。后来的重编舞不能直接用于 S6；若以较晚录像回溯早期版本，必须有版本一致的依据，否则另建版本或标版本待核。

| 可取得资料 | 可以做 | 不可冒充已完成 |
| --- | --- | --- |
| 只有曲名/发行目录 | 建曲目事实，标待评或沿用模拟默认值 | 根据团体风格直接确认四项参数 |
| 完整音源 + 歌词 | 歌唱要求初评，关键唱段候选 | 舞蹈要求、现场真实分工已确认 |
| 完整全景舞蹈视频，音源清楚 | 舞蹈要求评估、可见 dance-lead 结构 | 配音视频证明成员实际生唱能力 |
| 完整现场 + 全景/音源交叉核对 | 四项综合评估与职责结构复核 | 未呈现的声部/动作细节已核实 |
| 只有副歌短片或零散镜头 | 对可见片段标记特征与暂定范围 | 整曲峰值、最终 lead 数量 |

必须记录执行工具是否真的能听音频/看视频。仅取得网页文字、缩略图或视频链接，不算听看过。工具不具备感知能力时仍完成来源定位、候选整理、已有人工参数复用和未评项报告，不假造“已观看”或时间戳。

时间戳注明所属视频及版本；同名视频的相同时间位置不一定对应同一段。关键特征需要具体段落依据，至少覆盖主歌、副歌及实际存在的桥段/落サビ/dance break；没有这些段落的歌不强行凑齐。要定整曲评分须检查完整版本，不能只选最炫的一段。

### 10.4 难度量尺：直接使用现有1–20标尺

优先用 repo 已有、用户人工校准过的曲目建立约 12–20 首锚点，覆盖歌难舞易、歌易舞难和整体简单等组合。先记录其来源和版本；人工锚点是项目校准基准，不因此自动成为现实测量真值。不能自动重写锚点来迎合新规则。

沿用已经确定的 **1–20游戏难度标尺**，与作品S–D评级及trait的0–400无关。普通职业偶像歌曲的基础歌唱和基础舞蹈难度均以12为锚点；lead职责默认要求对应基础难度+2。若能力尺度上限也是20，推导值采用`min(20, base + 2)`；若当前实现允许超过20作为超上限门槛，则沿用实现并在总结中注明，不能自行假定。自动批量估计优先使用偶数，人工复核可使用奇数细调。

| 数值 | 含义 |
| --- | --- |
| 8 | 很简单、入门作品 |
| 10 | 较容易 |
| 12 | 普通职业偶像歌曲基准 |
| 14 | 明显有要求 |
| 16 | 高难歌曲 |
| 18 | 极高难度，需要顶级成员 |
| 20 | 极端上限，应当非常少 |

歌唱和舞蹈独立与锚点比较，不要求同步高低。资料不足时输出可能区间或使用明确标识的simulation default，不能制造个位数精度。

具体评分至少看以下特征，选择真正决定该曲档位的两到四项解释，不机械凑满：

| 轴 | 主要观察 | 防止误判 |
| --- | --- | --- |
| 歌 | 持续音区与音程变化、节奏/咬字密度、句长和换气、持续音/细微控制、确需现场完成的独立声部 | 最高音不是全部；录音和声不默认由现场成员承担；响亮不等于难 |
| 舞 | 节奏分割与groove、身体分离和协调、重心/平衡/转向、动作组合切换、控制精度、持续负荷 | BPM、动作幅度或跳跃次数不单独决定难度；简单动作的力度与节奏可能难 |

评分卡记录“整体基础值、关键峰值、最终导出值、理由、最近的较易/较难锚点”。最终导出依runtime字段含义确定，不能简单平均掉关键瓶颈；反过来，短暂非关键装饰动作也不自动拉高整曲门槛。

### 10.5 Sing-lead 数量：看关键职责，不数独唱人数

这里确定的是**游戏所需关键职责席位**。原舞台实际唱过独唱的成员可能很多，游戏仍只需要 1 个 sing-lead。记录实际演唱分工与推荐席位数时，使用不同字段。

先列出关键歌唱段落：落サビ、主旋律高负荷长句、核心 solo、确需真人同时承担的独立声部等。把连续或不重叠、可由同一人合理承担的段落归为同一职责；不同成员在现实中先后唱过，并不强制生成不同席位。

| 推荐数量 | 判定原则 |
| --- | --- |
| 1 | 默认结构：一个主要职责足以覆盖关键段落；其余是普通轮唱/齐唱，或不构成独立 lead 的配合 |
| 2 | 有两个实质关键职责：如两条同时发生的独立主声部，或明确双人对唱结构；也可因持续关键负荷需要分担，但必须给出段落与校准依据 |
| 3 | 存在三个可辨认且不可合理合并的关键职责；须逐一说明段落、同时性或分担必要性，不能只因三人唱功好就选 3 |

纯粹按人头数歌词分配、把每段独唱都当 lead、把 backing chorus 全算 lead，均不允许。负荷分担如果缺乏充分依据，记录 `1–2` 等待核区间，不武断认定生理上必须两人。

轻松齐唱型曲在本项目 1–3 约束下也可以设 1；它代表低强度核心职责，不代表该曲有高难主唱段。lead 数量与 lead 难度独立。

### 10.6 Dance-lead 数量：零必须是正常结果

| 推荐数量 | 判定原则 |
| --- | --- |
| 0 | 全员承担同质齐舞，没有需要独立关键舞者维持的突出职责；即使全员舞很难也可以是 0 |
| 1 | 有一个技术或结构上突出的核心舞蹈职责，如关键 solo/dance break 中无法由普通站位替代的任务 |
| 2 | 存在两个相互依赖的突出职责，如双人技术配合或两组各自承担实质关键任务；普通双center不够 |
| 3 | 三个明确独立、对本版本成立有实际作用的突出职责；每个都需单独证据 |

center、前排、镜头多、站中间跳同样动作，不自动构成 dance-lead。多个先后出现且可合并的 solo 不机械累加；一段全员高难齐舞应提高整体舞蹈要求，而非凭空产生 3 个 lead。

阵型中负责领位的人也不必是dance-lead；如果同时有突出的舞蹈职责，再评lead。

### 10.7 席位数量与阵容约束

- 各类 lead 数量不能超过该版本实际可表演人数；同一人可以兼任 sing-lead 与 dance-lead，因此不要要求两种数量之和小于人数。
- 兼任能否完成，需要检查关键唱段和舞段是否同时高负荷；无法兼任是具体配置约束，不是任意把数量加一。
- 如果证据显示需要超过游戏上限的独立关键职责，不默默截断为 3。保存完整观察、标记“超出模型表达范围”，在游戏抽象映射明确前不导入新值。
- 本轮默认不自动指定成员。明确需要指定时，按该版本的实际名单与来源核验，不能把现任主唱用于早期歌曲阵容。

### 10.8 自动化能做到哪一步

自动化重点是**抽取线索与辅助复核**，不是让音频/视频算法直接给出权威难度：

1. 从可访问素材提取时长、歌词段落、已明确标注的拍速/调性/credits及视频段落索引。
2. 有适用音频工具时，可试提取人声旋律、音符变化、段落密度等候选特征；必须检查伴奏、和声、分离误差及倍/半速误判，不把估计的音高/BPM冒充标注值。
3. 有可合法处理的清晰全景视频与适用视觉工具时，可辅助标记动作变化、换位、交错及突出舞段。镜头移动、遮挡、成员跟踪丢失都会限制推断；无法持续识别人时不输出看似精确的移动距离/队形复杂度。
4. agent结合实际听看、歌词与锚点形成四项候选和理由；高难值、多lead、版本冲突及低观察覆盖项优先复核。

仅为本轮补库不必引入完整姿态估计、说话人分离或自动乐谱转录工程。优先利用已可用能力；工具不支持时跳到证据定位与待评记录，不能由文本模型凭记忆补齐。

### 10.9 估计等级与缺资料兜底

四个字段分别记录状态；不要用一个“高置信度”掩盖部分字段根本没评过。

| 状态 | 使用条件 | 写入策略 |
| --- | --- | --- |
| `manual_preserved` | repo 已有人工设定 | 原样保留；发现疑点只列建议修订 |
| `assessed` | 相关完整素材已听看，版本明确，有特征证据并完成锚点比较 | 可导入兼容游戏字段，同时保留估计来源 |
| `provisional` | 部分素材或版本/分工不够清楚 | 输出候选档位/区间与理由；只有 repo 支持估计标识时才接入 |
| `unassessed` | 无对应可观察素材，或工具无法感知 | 不伪造评分；保留待评 |
| `simulation_default` | 运行必须有值而该字段未能评估 | 优先使用原有 fallback，明确是游戏初始化默认值，不计入已评覆盖率 |

默认值不依团体 tier、人气或歌名调整。本轮若 repo 完全没有 fallback，先在研究层建议“普通要求 + sing-lead 1 / dance-lead 0”作为临时初始化策略；须明确映射到现有量尺和使用位置后才接入。**缺资料的实际歌曲未因此被判定为简单、1主唱或0领舞。**

### 10.10 建议执行批次与评分卡

先完成基础歌曲检索，再用约 12–20 首有资料且覆盖不同难度结构的曲目校准本方案；优先复用已有人工锚点。这只是初始锚点集，不足以验证自动模型对4,000首的泛化准确率。按第15节分层试跑后，继续为可取得相应素材且落在处理预算内的歌曲批量评估，优先可玩团缺值、AI 常用曲与资料充分的代表曲。其余歌曲至少有明确的四字段状态，不因先校准就结束全库扫描，也不要求全库都完成完整听看。

评分卡最低包括：song/group ID、版本/人数/适用日期、已实际访问的素材和观察范围、关键段落时间戳、歌舞基础/峰值与导出值、最近锚点、sing-lead与dance-lead数量及职责说明、逐字段状态、映射规则版本。职责与详细特征可留在研究侧，不增加运行时逐part模拟。

以下是**虚构结构示例，不是任何真实歌曲的结论**：

| 结构 | 歌难度 | 舞难度 | sing-lead | dance-lead |
| --- | --- | --- | --- | --- |
| 全员普通轮唱，一个高要求落サビ | 基础12／lead16（override） | 12 | 1 | 0 |
| 歌唱普通，全员连续高难齐舞 | 12 | 16 | 1 | 0 |
| 关键双人对唱，动作温和 | 12／lead14 | 10 | 2 | 0 |
| 普通歌唱，单一突出技术舞段 | 12 | 基础12／lead16（override） | 1 | 1 |

检验方向：新增高音solo应主要影响sing-lead要求，新增全员高难齐舞不应自动增加dance-lead数；换成更强成员不应改变同版本作品要求。队形变化影响formation与队形熟练度，不改变歌曲难度。出现相反变化时回查语义或重复计分。

不要用本轮难度补全顺便自动生成歌曲质量、商业潜力、完整 formation、成员能力或逐句 part。技术难度与作品六项质量评价保持独立。

## 11. 安全合并与可重复运行

1. 为每条候选分类：新增、补空、明确更正、仅增来源、冲突待定、不满足时间边界、排除项。
2. 先产生可审阅 diff/dry run，再将证据充分且 schema 兼容的内容写入 canonical 源。无需对每个常规补空再次询问；冲突项目可暂存，不阻塞其他团。
3. 保留现有 ID、人工值、其他场景曲库与旧曲。不能为了 S6 过滤直接删除全局未来歌曲；应验证场景 loader 的筛选语义。
4. 新脚本应复用 repo 技术栈，支持稳定去重与幂等执行；相同输入及证据再次运行不得重复新增、漂移 ID 或重排全部数据。
5. 若只需一次少量修改，可用现有工具完成，不必搭建完整爬虫平台。对批量更新，保存足够证据与变更清单以便继续执行。
6. 小型 schema/loader 修正必须由已发现的具体缺陷驱动，记录前后行为；跨模块重构另列建议。无法安全接入的记录留在候选集，并说明原因。

## 12. 输出与验证

优先复用同用途现有文件，否则在 `support/reports/` 下建议生成：

| 产物 | 内容 |
| --- | --- |
| `scenario6-song-update-audit.json` | 输入身份、每团基线/更新后统计、检索状态、剩余任务；同一文件保留 before/after |
| `scenario6-song-update-evidence.jsonl` | 可追溯的字段级证据和必要 setlist 样本；如 repo 有独立 setlist 文件则引用 |
| `scenario6-song-performance-assessments.jsonl` | 歌舞难度、lead数量、版本/人数、段落特征、锚点、逐字段状态和runtime映射；一行一歌曲版本 |
| `scenario6-song-update-jobs.jsonl` | 若repo无同类机制，保存可续跑任务状态、输入/素材指纹、失败原因、重试和下一步；可复用现有数据库/任务机制 |
| `scenario6-song-update-changes.jsonl` | 实际应用及待定变更、old/new、原因和证据引用；更正日志仅供审计 |
| `scenario6-song-update-summary.md` | 中文结论、真实数量、主要缺口、schema 判断、验证结果和接续入口 |

文件名可适配既有规范，不重复创建同类体系。运行时只加载 canonical 数据；冲突与更正日志不进入一般内容检索入口。

验证应覆盖实际风险：

- JSON/schema 通过；稳定 ID 无重复，group/song 引用无悬空，新增 source 引用可定位。
- before/after 可对账：新增作品数、团曲关联数、补空字段数、更正数与隔离数分开统计。
- S6 实际加载结果符合日期规则；未来出道团/未来歌未泄漏，已确认先演后发行的歌未被错误排除。
- 至少检查活跃零曲团、已有完整度较高团、未来出道团；如新增数据涉及翻唱、重发、日期未知或部分 setlist，再检查相应样例。
- 既有可玩团人工属性及其他场景数据未被意外覆盖；全局旧曲和未来曲保留。
- 歌舞1–20量尺/字段语义映射正确；普通基准12，lead默认要求对应基础+2；sing-lead 1–3、dance-lead 0–3且各自不超过人数；缺资料默认值与已评值可区分。
- 数据模型及运行逻辑中不存在formation difficulty；抽查全员难舞但dance-lead 0、普通轮唱但一个高要求sing-lead等结构，避免歌舞联动或把中心位误算为lead。
- 批量更新脚本重复运行无新增差异；沿用 repo 现有数据检查命令。修改 loader 时增加/运行与具体缺陷对应的测试，不为了报告生成重复测试。

最终总结写明处理团数、新增去重歌曲数、S6 确认可用增加数、未来候选数、仍为零曲/日期不明的团，以及具体未完成原因。来源不可访问或检索预算耗尽都如实记录；完成本轮流程不等于史实曲库已核全。

四项表演参数另做逐字段覆盖统计：人工保留、已评、暂定、未评、模拟默认值分别计数；报告本轮实际听看曲数和版本冲突数，不能用“每首都有数字”代替评估覆盖率。

## 13. 回答 groups.json 是否需要优化

根据实际检查结果给结论，不预设必须修改：

- 歌曲资料缺失，应主要补 song 数据、团曲关联与研究证据。
- 团体稳定 ID、别名或生命周期问题导致无法关联/判断开档状态，才提出对应的最小修改。
- playable/selectable、tier 或场景状态已有权威配置时，避免再写一份到 groups.json 形成双重来源。
- 不把 setlist、歌词、歌曲难度、成员 part、formation 或频率统计塞进 groups.json。

总结区分：本轮已修的数据问题、已证实需改的结构问题、暂不需要改的设计。附实际文件和字段依据，不只给泛泛建议。

## 15. 约4,000首的全库处理与增量方案

### 15.1 明确可以完成和不能保证的范围

程序可以遍历每一条歌曲记录、查重、检查字段和日期、建立来源索引、保留人工值、分配待处理状态，并按现有规则提供运行所需默认值。**不能保证每一首都有完整音源/全景视频，也不能保证每一首的歌舞难度和lead数都能被可靠观察确定。**

“扫完”应有三种独立口径：

| 指标 | 分母/分子 | 目标 |
| --- | --- | --- |
| 全库扫描覆盖 | 当前输入快照的去重目标版本中，完成基础检查并获得明确状态的数量 | 全部；失败项也必须可追踪，但不算成功评估 |
| 初始化数值覆盖 | runtime要求四项值的目标版本中，具备兼容数值/可用fallback的数量 | 在既有fallback或明确映射支持下争取全部 |
| 逐字段证据评估覆盖 | 各字段目标版本中，已依相关完整素材和校准流程评估的数量 | 如实报告；不得以默认值或部分素材凑足 |

人工保留的参数另列，是否有来源不因本轮保留而升级；有基础元数据不等于四项表演参数都已评估。总数同时报告作品实体数、团曲关联数、实际待评版本数，不能把4,000条发行记录当成4,000首独立作品。

假设每首4分钟，4,000首完整播放一遍就是约267小时素材，还没计检索、比对及判断。这只是量级示例，不是当前库的实测时长，也不代表机器处理一定需要267小时。实际吞吐取决于素材可得性、工具能力和处理预算，须由试跑测得。

### 15.2 五阶段处理，不给每首重复做同一套搜索

**阶段A：全库本地检查。** 一次扫描所有记录，合并稳定身份和重复发行，建立每首四字段状态；读既有人工参数、证据、版本和素材。此阶段不调用逐曲外部搜索，不因缺素材而阻塞。

**阶段B：团体/发行批次建立来源索引。** 先按团体取得官方曲库、发行页、专辑tracklist、官方频道及已有setlist；一页能覆盖多首就一次读取复用。共享MV/发行对象按URL或平台ID缓存。仅对未匹配或有冲突的曲目做单曲搜索；不要为4,000首各跑一遍同样的团体查询。

**阶段C：证据适配的批量评估。** 有完整音源先评歌唱；有全景视频再评舞蹈及相应lead。不同字段独立推进。实际具备音视频感知与处理能力才运行对应任务；官方文字或可靠已整理分析能支持的字段单独注明证据路线。音频评估成功不自动触发舞蹈评估成功。

**阶段D：估计/默认值与重点复核。** 资料不足时保留现有游戏默认值或暂定候选；明确低置信度与未评。优先复核重要曲、极端档位、sing-lead 3、dance-lead 2–3、版本冲突和异常变更，同时从普通结果中做分层随机抽查，避免只看极端值漏掉系统性偏差。

**阶段E：增量合并。** 按批验证并合并事实及兼容的估计；保存剩余队列。新增歌只入新任务，补到素材只重跑受影响字段，其他已完成项不重新搜索。保留原始证据与已提取特征，使量尺映射更新不必重新下载和分析全部视频。

### 15.3 试跑决定能自动化多少，不预先承诺覆盖率

先从全库分层取约60–100首试跑（样本不足时取全部），包含可玩/AI、不同年份/团体、单曲/合集重复、音源齐全/只有MV/资料少、简单/高难候选。不要只选熟悉团的热门歌曲。

记录每阶段耗时、缓存命中、访问失败、素材可用、四字段成功/暂定/未评比例。已有人工标签中，可将部分作为锚点，另一部分留作未参与校准的检查集；标签不足时不声称已验证自动评估准确率。

难度看相差几档及偏高/偏低倾向；lead数看具体错分情形，尤其不能让“全部dance-lead=0”因类别不平衡显得准确。游戏职责数本来就是设计估计，与实际独唱人数不一致不自动算错。

用实测结果估算剩余任务的检索/感知调用量与耗时，写清外推假设。资源条件不满足时完成全库A阶段、可完成的B阶段和初始化检查，留下可续跑的C/D队列；不暗示一个聊天agent能在本轮自动观看全部视频。没有专门授权，不开通付费API、购买素材或产生额外付费批处理任务。

### 15.4 任务身份、缓存、断点与失败处理

复用repo已有批处理框架；没有时用小型脚本及JSONL/现有数据库实现，不为本次补库搭建服务平台。

- 任务键包含稳定歌曲ID、表演版本/阵容和目标字段；输入指纹覆盖相关数据与版本，记录素材URL/ID及可取得的内容指纹、特征提取器版本、评分规则版本。
- 状态至少区分待处理、处理中、已评、暂定、缺素材、访问失败、冲突待核和人工保留；成功处理元数据不能让四项评估任务整体变为成功。
- 每批例如25–100首，实际大小按耗时和接口限制调整。每首完成就可checkpoint；写文件用临时文件替换或repo的事务方式，避免中途退出破坏结果。保留日志但不把巨大素材复制进git。
- 搜索/读取在平台允许范围内有限并发、限流、退避；写canonical数据有序进行。为临时失败设置有限重试，永久缺素材/权限限制不无限重试。
- 中断后恢复未完成任务；对已有有效结果不重复调用外部工具。进度同时显示扫描、素材匹配、四字段评估和待处理数。
- 输入、素材或规则变化只使相关阶段失效。例如标题别名修正不应自动重算已确认编舞；难度映射改变可复用有效特征；新编舞版本须重新评舞蹈与dance-lead。
- 失效/过期结果保留历史身份，但不冒充已按新规则重评。不得覆盖用户新的人工修改。

### 15.5 允许估计，但不要把“全库有数字”当作测量完成

对于游戏初始化，稳定、可解释的估计可以有用。已观察到局部特征时可给`provisional`档位或范围，实际写入的代表值需有固定映射并保存不确定性；完全没素材时优先使用既有`simulation_default`。

不要按团体tier直接抬高难度，也不要同团全部复制同一套已评结果。同一歌曲相同版本可复用分析；翻唱改调/重编舞/变更人数时只复用仍适用的部分。

若以后训练特征到难度的预测模型，需有足够且覆盖目标分布的标注与独立验证，再引入`model_estimated`状态；近邻或同风格推断也属于预测。**不能用12–20首锚点就宣称能准确预测全库**。本次不预先要求搭建机器学习模型；先交付可运行的扫描与证据分层流程。

最终可接受的完成状态是：全部目标记录已检查并可追踪，有证据的已评并合并，缺素材的有明确fallback/未评状态和接续任务，已有人工值受保护。用户以后添加歌曲或素材时，可沿同一流程更新，而不是重新研究全部4,000首。
