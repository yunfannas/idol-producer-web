# Admin Job Shrink Design

## Purpose

With monthly strategy in place, routine admin jobs should shrink.

The player should feel like a producer setting direction, then reviewing consequences, not a clerk rebalancing tiny defaults every few days.

Admin jobs should become:

```text
generated by strategy
reviewed as summaries
changed only as exceptions
```

## Design Rule

Every admin control should answer one question:

```text
Is this a meaningful producer decision, or should the strategy/scheduler handle it?
```

If it mainly changes an outcome by tiny numeric tuning, shrink it.

If it creates a real tradeoff, keep it.

## Admin Job Classification

| Current job | New role | Reason |
|---|---|---|
| Live frequency defaults | Strategy Meeting | Core direction, not daily admin. |
| Benefit-session default | Strategy Meeting | Split into online / shooting-handshake / post-live tokutenkai policy. |
| Goods enabled per live | Strategy-generated default, live exception | Usually follows live type and strategy. |
| Auto goods refill | Inventory threshold, not prominent policy | Should not be a major gameplay knob. |
| Per-member SNS platform checkboxes | Content strategy + member role defaults | Too granular for normal play. |
| Stream hours by platform | Content block generated by strategy | Avoid weekly hour min-maxing. |
| Training default sliders | Training philosophy / role development | Keep detailed edits only for focused member development. |
| Per-member training sliders | Training page exception / development plan | Useful, but should not be required daily. |
| Prerecorded vocals | Live production exception | Too technical for normal policy. |
| Rehearsal start/end | Generated from live type and risk | Manual override only for important lives. |
| Tokutenkai timing/slot details | Generated from benefit policy | Manual override only for selected lives. |
| Goods price/stock | Making/Goods page | Keep as production/inventory task, not schedule policy. |
| Vacation/off days | Member health exception | Keep because it is a real human-management decision. |
| Scouting/auditions | Strategic roster decision | Keep as dedicated system, tied to strategy. |
| Contract/scandal/graduation | Blocking decision | Keep as high-stakes event. |

## Live Editor Simplification

Combine `New Live` and `Modify Live` into one live arrangement page.

The top of the page should have a selector:

```text
Live to arrange:
[ New live ]
[ Duplicate from upcoming live... ]
[ Upcoming live A ]
[ Upcoming live B ]
[ Upcoming live C ]
```

This replaces separate mental modes:

```text
New Live
Scheduled / modify live
```

with one editor:

```text
select source
-> edit live details
-> schedule / save changes
```

### Selector Modes

| Mode | Behavior |
|---|---|
| `New live` | Starts empty editor with strategy-generated defaults. |
| `Upcoming live` | Loads that scheduled live for modification. |
| `Duplicate upcoming live` | Copies selected live as a template, but creates a new unscheduled draft. |

### Duplicate Safety Rule

When duplicating an upcoming live, clear fields that must be intentionally reselected:

```text
date
start time
end time
rehearsal start
rehearsal end
tokutenkai start
tokutenkai end
venue booking hold / external schedule uid
result uid
played status
notification dedupe keys
```

Keep template fields:

```text
live type
title template
venue preference, if still available
ticket prices
VIP settings
setlist / program
tokutenkai enabled flag
tokutenkai ticket price
tokutenkai slot seconds
expected tokutenkai tickets
goods enabled flag
goods selection
staffing assumptions
```

The editor should visibly mark duplicated drafts as needing a new slot:

```text
Duplicated draft: choose a new date and time.
```

Save button remains disabled until a valid new date/time slot is selected.

### Suggested Lives Tabs

After combining new/modify, Lives can become:

```text
Arrange
Upcoming
Reports
Festival
League
```

`Arrange` is the unified editor. `Upcoming` is a compact list for browsing/selecting scheduled lives, and selecting a row can jump back to `Arrange` with that live loaded.

### Schedule Calendar Shortcut

Double-clicking a scheduled live from the Schedule calendar should open live modification directly:

```text
Schedule calendar
-> double-click scheduled live item
-> navigate to Lives / Arrange
-> load selected live in modify mode
```

This should target the live item itself, not empty day space. Empty day double-click can keep its current behavior of focusing/showing that week.

If a day has multiple scheduled lives, the UI should either:

- double-click a specific live pill/list item; or
- open a small picker, then route the chosen live to `Lives / Arrange`.

Route state:

```text
nav = Lives
lives_tab = Arrange
selected_live_uid = clicked_live_uid
editor_mode = modify
```

## New Admin Surface

Replace broad always-editable policy with three smaller layers.

### 1. Strategy

Monthly meeting only.

Owns:

- live load;
- benefit-channel mix;
- media/IP emphasis;
- viral/content emphasis;
- production investment;
- rest protection;
- member exposure policy;
- roster renewal direction.

### 2. Operations Summary

Read-only most of the time.

Shows:

- this month's generated schedule;
- training load summary;
- content blocks;
- benefit sessions;
- goods inventory risk;
- staff capacity;
- unresolved exceptions.

This can live inside the Strategy `Projection` tab or a small Operations panel.

### 3. Exceptions

Editable, but scoped.

Examples:

- adjust one important live's setlist, goods booth or tokutenkai plan;
- give one member rest;
- push one member's development focus;
- order goods when stock is low;
- approve emergency PR / contract / graduation decision.

Exception edits should be traceable:

```text
reason
affected date/member/live
expected cost
expected benefit
```

## Shrunk Policy Model

The old `GroupPolicy` can remain for compatibility, but it should become generated operational defaults.

Suggested split:

```ts
interface GroupStrategy {
  // monthly producer direction
}

interface GeneratedOperationsPlan {
  month: string;
  live_defaults: LiveOpsDefaults;
  benefit_defaults: BenefitOpsDefaults;
  content_defaults: ContentOpsDefaults;
  training_defaults: TrainingOpsDefaults;
  goods_defaults: GoodsOpsDefaults;
}

interface OperationException {
  uid: string;
  date: string;
  scope: "live" | "member" | "goods" | "training" | "content" | "crisis";
  reason: string;
  payload: Record<string, unknown>;
}
```

`GeneratedOperationsPlan` is created after strategy finalization. `OperationException` stores player overrides.

## What To Remove From Normal Policy UI

Do not show these as prominent normal controls:

- generic tokutenkai on/off;
- generic goods on/off;
- per-member SNS platform checkboxes;
- stream hours per week by platform;
- default training sliders;
- prerecorded vocals checkboxes;
- auto refill quantity.

They can move to:

```text
Advanced Operations
```

or become generated defaults with warning/edit affordances only when relevant.

## What To Keep Prominent

Keep these as dedicated, meaningful pages:

| Page | Keep because |
|---|---|
| Strategy | Monthly direction and tradeoffs. |
| Lives | Concrete live scheduling, setlist, reports. |
| Training | Member growth, roles, formation, health. |
| Making/Goods | Production and inventory decisions. |
| Scout | Roster pipeline and auditions. |
| Inbox | Blocking high-stakes decisions. |
| Fans/Audience | Consequence reading and diagnosis. |

The difference is that these pages should not require daily micromanagement to avoid bad outcomes.

## Autopilot Defaults

When strategy is finalized, generate operations.

Examples:

### `=LOVE` / mature IP sustain

- low underground live frequency;
- online benefit and release-event blocks;
- media/content blocks;
- protected rest;
- high production investment;
- no post-live tokutenkai by default.

### `iLiFE!` / high-frequency growth

- frequent lives;
- post-live tokutenkai enabled on suitable lives;
- higher goods turnover;
- higher fatigue warning sensitivity;
- content blocks around live momentum.

### `Nogizaka46` / generational renewal

- release/tour/media driven calendar;
- shooting/handshake release-event blocks;
- roster-renewal and selection review;
- high production and media load;
- post-live tokutenkai disabled.

## Player-Facing Warnings

Instead of asking the player to tune every detail, show warnings.

Examples:

```text
Goods stock may run out at two high-demand lives.
```

```text
Three members are over the planned workload for this month.
```

```text
Your current content plan is growing public awareness, but otaku conversion is below projection.
```

```text
Post-live tokutenkai capacity is below core demand for this live.
```

Each warning can have a focused action:

```text
Review live
Rest member
Order goods
Discuss next month
Ignore
```

## Notification Rule

Do not add routine admin notifications.

Keep blocking notifications for:

- Monthly strategy meeting;
- Today's live schedule;
- Live report;
- cash crisis;
- scandal / contract / graduation;
- major venue/release commitment.

Routine admin issues should appear as dashboard warnings, not inbox interruptions.

## Minimal Implementation

1. Keep existing `GroupPolicy` data for compatibility.
2. Hide or demote Schedule > Policy into `Advanced Operations`.
3. Add an Operations Summary panel to Strategy Projection.
4. Generate default live/benefit/training/content/goods assumptions from finalized strategy.
5. Convert routine admin inbox items into page warnings where possible.
6. Keep manual overrides on Lives, Training, Goods and crisis decisions.

This preserves the realistic administrator feel, but makes it optional and situational instead of the main gameplay burden.
